## 1. خريطة النشر

| البيئة | المنصة | قاعدة البيانات | متى تُستخدم |

## 2. Vercel — الإعداد (مرة واحدة)

1. ادخل [vercel.com](https://vercel.com) → **Add New Project** → استورد `tarikchouika/F-W-M-S` من GitHub.
2. إعدادات البناء تُكتشف تلقائيًا (Next.js). لا حاجة لتخصيص.
3. أضف **Environment Variables** (Production + Preview):
   - `DATABASE_URL` — قاعدة البيانات السحابية (أو `file:./db/preview.db` للمعاينة).
   - `AUTH_SECRET` — سر جلسات JWT (توليد: `openssl rand -base64 48`).
   - `NEXTAUTH_URL` — نطاق النشر.
4. Deploy. كل push إلى `main` = نشر تلقائي. كل PR = رابط معاينة.
5. أضف نطاق Cloudflare إلى المشروع (Step 3) واتبع تعليمات DNS.

## 3. Cloudflare — الإعداد

**معرّف الحساب:** `758fcc827f3338772847c28391b6c6c3` — **رمز الـ API يُحفظ في `.env`/أسرار المنصات فقط ولا يُكتب في أي ملف مرفوع.**

### 3.1 DNS للنطاق السحابي (Vercel)
في لوحة Cloudflare → DNS → سجلات تشير إلى نطاق Vercel (`cname.vercel-dns.com`) حسب تعليمات Vercel عند إضافة النطاق. وضع الوكيل (Proxy) اختياري.

### 3.2 Tunnel للخادم المحلي (الهاتف)

```bash
# على الهاتف (Termux/Ubuntu) — بتنسيق cloudflared:
cloudflared tunnel login
cloudflared tunnel create fwms-local
cloudflared tunnel route dns fwms-local fwms-local.<نطاقك>
cloudflared tunnel run --url http://localhost:3000 fwms-local
```

- ملف الإعداد المرجعي: `infra/cloudflare/tunnel.example.yml` (بلا أسرار).
- الخادم المحلي يصبح متاحًا عبر `https://fwms-local.<نطاقك>` بلا فتح أي منفذ.
- **التحقق الجغرافي للحضور يبقى إلزاميًا في الوضعين** على الخادم نفسه (SPEC §4.2) — النفق مجرد نقل، لا يغيّر قواعد التحقق.

## 4. سياسة الأسرار (نافذة)

| السر | أين يُخزَّن | ممنوع |
|---|---|---|
| GitHub PAT | مدير اعتمادات git المحلي فقط (أو GitHub CLI) | ❌ في أي ملف مرفوع |
| Cloudflare API Token | `.env` على الجهاز المخوَّل + أسرار Vercel عند الحاجة | ❌ في الكود/التوثيق |
| Vercel Token | أسرار GitHub Actions عند أتمتة النشر | ❌ في الكود |
| `AUTH_SECRET` | `.env` / متغيرات Vercel | ❌ في الكود |
| روابط قاعدة الإنتاج | متغيرات المنصة | ❌ في التوثيق |

**عند اشتباه تسريب:** إبطال فوري من لوحة الجهة → تنظيف تاريخ Git إن لزم → تدوير كل الأسرار → إبلاغ في `docs/WORKLOG.md`.

**الدفع من بيئة بلا مدير اعتمادات** (بيئة التطوير السحابية أو Termux):
```bash
FWMS_GITHUB_TOKEN=ghp_xxxxxxxxxxxx ./scripts/push.sh   # يدفع main + الوسوم
```
التوكن كمتغير بيئة فقط — يُبطل فور انتهاء الحاجة، ولا يُخزَّن في أي ملف.

## 5. التحقق بعد أي نشر (قائمة فحص)

- [ ] لوحة التحكم تعرض بيانات حسب الدور.
- [ ] لا أخطاء في لوغات الخادم.
- [ ] (محليًا) نسخة احتياطية بعد أول تشغيل ناجح.

## 6. الانتقال بين البيئتين (SPEC §7) — إجراء مُختبَر (المرحلة 8)

> **مُختبَر فعليًا 2026-10-17** (جلسة المرحلة 8): نسخة عبر VACUUM INTO ثم فحص تطابق
> (quick_check + 35 جدولًا × 401 صفًا متطابقة) ثم إقلاع البيئة الثانية كخادم إنتاج standalone ثم
> تطابق دخول + قراءات API (شركات/تدقيق/مسارات) — الدليل في WORKLOG قيد المرحلة 8.

**محلي ← عام (والعكس):**

```bash
# 1) نسخة احتياطية سليمة أثناء التشغيل + فحص تطابق آلي (أداة موثقة بالمستودع)
bun scripts/transfer-between-env.ts <المصدر.db> <الهدف.db>
#    أو على الهاتف بـ sqlite3: sqlite3 المصدر.db "VACUUM INTO 'الهدف.db'" + PRAGMA quick_check

# 2) شغّل البيئة الجديدة على النسخة
#    (الخادم المستقل يقرأ PORT/HOSTNAME/DATABASE_URL من البيئة — درس WORKLOG)
env NODE_ENV=production PORT=<منفذ> HOSTNAME=0.0.0.0 \
  DATABASE_URL=file:<المسار الكامل للهدف.db> \
  AUTH_SECRET=<openssl rand -hex 32> \
  bun .next/standalone/server.js

# 3) تحقق: /api/health + دخول مستخدم بذور + مقارنة عدد السجلات لكل جدول
#    (سكربت transfer-between-env يقوم بالمقارنة آليًا)
```

- **تنبيه مهم:** لا يُنقل `AUTH_SECRET` مع القاعدة — للبيئة الجديدة سرها الخاص (تدوير مستقل).
- الأداة المرجعية للنسخ اليومية: `infra/termux/backup.sh` (المساعد الثاني — Online Backup API + quick_check) —
  والإجراء أعلاه للنقل الكامل بين بيئتين.
- كل نقل يُوثّق في WORKLOG (المصدر/الهدف/البصمات/من نفّذ).

## 7. دليل التشغيل اليومي (SPEC §8 — المرحلة 8)

| المهمة | الإجراء | الدورة |
|---|---|---|
| فحص الصحة | `curl https://<البوابة>/api/health` ثم التحقق `status:ok` و`database:ok` | يوميًا (أو مراقبة خارجية تصيب هذا المسار) |
| النسخ الاحتياطي | `infra/termux/backup.sh` (تدوير 7/4/6 موثق فيه) | يوميًا تلقائيًا |
| التحقق من النسخة | فحص وجود ملف اليوم + `quick_check` (السكربت يفعله ويوقف عند الفشل) | أسبوعيًا يدويًا |
| استعادة مُختبَرة | إجراء §6 أعلاه على قاعدة تجريبية — لا أول استعادة وقت الكارثة | ربع سنوي |
| سجل التدقيق | لوحة ثم التدقيق: بحث عن `auth.login.failed` المتكرر | أسبوعيًا |
| تحديث الأسرار | تدوير `AUTH_SECRET` + توكنات البنية عند أي شك — إجراء الإبطال في OWNERSHIP_TRANSFER §5 | عند الحاجة |
| نقل الملكية | أداة `/dashboard/platform` + دليل docs/OWNERSHIP_TRANSFER.md | عند الطلب |

### ملاحظات أداء الخادم المحلي (مُنفّذة المرحلة 8)

- لوغ استعلامات Prisma معطل في الإنتاج (`src/lib/db.ts`) — كان يطبع كل استعلام على الهاتف.
- توليد المستندات في عملية ابنة معزولة لا تحجب خادم الحضور (المرحلة 7).
- ترويسات أمنية + إخفاء X-Powered-By في `next.config.ts` (docs/SECURITY.md).
- **مقترح للمساعد الثاني:** قياس زمن استجابة `/api/attendance/check-in` قبل وبعد التحديث على الهاتف
  واقتراح فهارس إن لزم (ملكية المخطط له — عبر WORKLOG).
