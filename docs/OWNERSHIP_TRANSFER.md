# docs/OWNERSHIP_TRANSFER.md — دليل نقل ملكية المنصة (SPEC §3.2 — المرحلة 8)

> **مالك هذه الوثيقة: المساعد الأول.** نقل ملكية منصة FWMS يتم **بأداة إدارية موثّقة** (هذا الدليل)
> لا بتعديل يدوي في القاعدة — نص SPEC §3.2 الحرفي. الأداة: واجهة `/dashboard/platform` + واجهة
> `/api/platform/ownership`، والمحرك `src/lib/ownership.ts`، والاختبار المُوثَّق `tests/api-phase8.ts` (76/76).

---

## 1. متى تُستخدم هذه الأداة؟

- بيع المنصة أو تسليمها لجهة وصية (وزارة/مؤسسة عمومية) أو شركة خاصة.
- تغيير الكيان القانوني المالك (إعادة هيكلة، اندماج).
- **ليست** لتغيير الهوية البصرية فقط — لذلك استخدم «تحديث هوية المالك» في الصفحة نفسها (white-label) دون نقل.

## 2. شروط مسبقة (كلها إلزامية)

1. **الشخصان**: مشغّل حالي يملك حساب `super_admin` ساريًا + تواصل موثوق مع المالك الجديد (قناة خارج النظام).
2. **بيانات المالك الجديد**: الاسم القانوني، الاسم المعروض، بريد اتصال، وبريد **حساب ابتدائي جديد** (غير موجود بالنظام — الأداة ترفض البريد الموجود حماية من الاستيلاء على حساب قائم).
3. **فضاء كافٍ للقرص** لمخرجات النقل بجوار القاعدة (`db/ownership-transfers/`): نسخة `.db` + تصدير `.json`.
4. وصول المشغّل إلى `.env` (لتدوير `AUTH_SECRET` — الخطوة 7).

## 3. دورة النقل (آلة الحالات)

```
(لا نقل)
   │ initiate — بإعادة مصادقة كلمة المرور + بيانات المالك الجديد
   ▼
awaiting_current_owner  ──(تجميد التغييرات الإدارية يبدأ فورًا: 423 platform_frozen
   │                      على إنشاء/تعديل الشركات ومنح المحاسبين)
   │ approve-current — موافقة المالك الحالي (خطوة 1 — إعادة مصادقة)
   ▼
awaiting_new_owner
   │ issue-code → رمز 10 محارف يُعرض مرة واحدة — يُسلَّم للمالك الجديد خارج النظام
   │ approve-new — إدخال الرمز (خطوة 2 — إعادة مصادقة) — الرمز أحادي الاستخدام
   ▼
approved
   │ execute — إعادة مصادقة ثم (بالتتابع داخل الأداة):
   │   أ. VACUUM INTO نسخة احتياطية كاملة + SHA-256
   │   ب. فحص تطابق (quick_check + عدد الجداول مطابق للمصدر)
   │   ج. تصدير مفتوح JSON لكل جدول (BLOBs بـ base64 موسوم) + SHA-256
   │   د. معاملة ذرّية: تبديل كيان المالك (id ثابت) + إلغاء كل عضويات
   │      super_admin + إنشاء حساب المالك الجديد الابتدائي + إبطال جلسات كل المستخدمين
   │   هـ. رفع التجميد + حدث ownership.transfer.completed في التدقيق
   ▼
completed — ثم (خارج الأداة): تدوير الأسرار وتأكيدها بـ confirm-rotation
   (أي حالة قبل completed): cancel — بإعادة مصادقة + سبب، ويرفع التجميد
```

**لماذا موافقتان منفصلتان؟** SPEC §3.2: «موافقة صريحة من المالك الحالي والجديد (خطوتان منفصلتان)».
موافقة الجديد تصل عبر رمز يسلمه المشغّل له خارج النظام (بريد/رسالة موثوقة) — لا يمكن للمالك الحالي
وحده إتمام النقل، ولا للجديد وحده.

**قرار موثَّق (المصادقة الثنائية):** SPEC يطلب «بمصادقة ثنائية» لخطوتي الموافقة. النظام لا يطبّق TOTP
بعد (حقل `twoFactorEnabled` جاهز بالبنية). الضابطات النافذة المعوّضة: **إعادة مصادقة كلمة المرور في كل
خطوة + رمز أحادي الاستخدام خارج النظام**. ترقية 2FA عند تفعيلها عمومًا ستغطي هذه الخطوات تلقائيًا
(المسار نفسه يعتمد إعادة المصادقة). موثَّق كذلك في docs/SECURITY.md §6.

## 4. خطوات التنفيذ العملية (المشغّل)

1. سجّل الدخول بـ `super_admin` وافتح **لوحة التحكم ← ملكية المنصة**.
2. قسم «نقل ملكية المنصة»: املأ بيانات المالك الجديد + سبب النقل + **كلمة مرورك** ← «بدء نقل الملكية».
   - من هذه اللحظة: التجميد الإداري مفعّل (تظهر لافتة الثلج في الصفحة) — الشركات والمنح تُقرأ ولا تُعدّل.
3. «الموافقة بصفة المالك الحالي» (+ كلمة المرور).
4. «توليد رمز موافقة المالك الجديد» (+ كلمة المرور) → **انسخ الرمز فورًا** (يظهر مرة واحدة) وسلّمه
   للمالك الجديد عبر قناة موثوقة.
5. عند استلام المالك الجديد موافقته (يقرّ بالمحتوى والغرض): أدخل الرمز ← «إدخال رمز الموافقة».
6. «تنفيذ النقل» (+ كلمة المرور). الاستجابة تعرض **مرة واحدة**:
   - كلمة المرور الابتدائية لحساب المالك الجديد — انسخها وسلّمها له (يُنصح بتغييرها فور أول دخول).
   - قيمة مقترحة لـ `AUTH_SECRET`.
   - بصمات SHA-256 للنسخة الاحتياطية والتصدير + نتيجة فحص التطابق + عدد العضويات الملغاة والجلسات المبطلة.
   - **تنبيه:** جلسة المشغّل نفسها تُبطَل بالتنفيذ (كل الجلسات تموت) — أعد الدخول بحساب المالك الجديد.
7. **تدوير الأسرار (إلزامي — خارج الأداة):**
   - ضع `AUTH_SECRET` الجديد في `.env` (القيمة المقترحة أو `openssl rand -hex 32`).
   - دوّر أسرار البنية الأخرى إن وُجدت: توكن Cloudflare Tunnel، مفاتيح VAPID، توكن GitHub للنشر —
     كل سر عرفه المالك السابق أو مطوّره يُعدّ مكشوفًا بعد النقل.
   - أعد تشغيل الخادم (`infra/termux/start-server.sh` — الطريقة المعتمدة setsid الموثقة).
   - سجّل الدخول بحساب المالك الجديد ← «تأكيد تدوير الأسرار» — يختم السجل ويغلق البند.

## 5. ماذا يحدث للمالك السابق؟ (معيار القبول — مُثبت باختبار 76/76)

| الأثر | الدليل من الاختبار |
|---|---|
| كل جلساته (وكل جلسات المنصة) تنتهي فور التنفيذ | طلباته التالية = 401 |
| عضويته `super_admin` تُلغى — **إعادة دخوله مرفوضة** بـ `no_active_membership` | لا باب خلفي ولا حساب صيانة |
| حساباته الأخرى غير الإدارية (إن كان موظفًا مثلًا) لا تُمسّ | عضوية المدير بقيت — يعيد الدخول بكلمة مروره |
| سجل التدقيق كامل: كل قيود ما قبل النقل محفوظة + أحداث الدورة كلها | تطابق القيود قبل/بعد في الاختبار |
| هوية المالك في كل الواجهات والتقارير تصبح للمالك الجديد | القسيمة بعد النقل = إصدار جديد v2+ بتذييل المالك الجديد |
| مستنداته المولدة سابقًا ثابتة لا تُمسّ | v1 محفوظة كما هي (مبدأ الثبات) |

## 6. مخرجات النقل على القرص (للتدقيق طويل الأمد)

في `db/ownership-transfers/` (بجوار القاعدة — لا تُرفع إلى git):

- `ownership-<معرّف>.db` — نسخة احتياطية كاملة ما قبل النقل (SQLite سليم، فحص quick_check اجتاز).
- `ownership-<معرّف>.json` — تصدير بصيغة مفتوحة: كل جدول + صفوفه، والثنائيات (BLOB) بـ base64 موسوم
  `{"__blob_b64": "…"}` — قابل للقراءة بأي أداة.

كلاهما بصمة SHA-256 مخزنة في سجل النقل — أي تعديل لاحق يُكشف بمقارنة `sha256sum`.

## 7. استعادة/تراجع

- **قبل التنفيذ:** `cancel` يلغي كل شيء ويرفع التجميد — لا أثر متبقٍّ سوى قيد تدقيق.
- **بعد التنفيذ:** لا «تراجع» مباشر (النقل حدث) — الاستعادة تعني **نقلًا عكسيًا** بالنفس الأداة، أو
  استعادة نسخة `ownership-<id>.db` بإجراء النقل بين البيئتين (DEPLOYMENT.md §6). سجل التدقيق يوثق كل شيء.

## 8. أعطال معروفة ورسائلها

| الرمز | المعنى | ماذا تفعل |
|---|---|---|
| `reauth_failed` | كلمة المرور غير صحيحة | أعد إدخالها — كل خطوة تتطلبها |
| `transfer_in_progress` | نقل جارٍ بالفعل | أكمله أو ألغه قبل بدء آخر |
| `admin_email_exists` | بريد الحساب الابتدائي مستخدم | اختر بريدًا جديدًا (حماية استيلاء) |
| `approval_code_not_issued` | لم يُولَّد رمز بعد | «توليد رمز» أولًا |
| `approval_code_mismatch` | الرمز خاطئ | طلب رمزًا جديدًا من المالك الجديد |
| `integrity_check_failed` | النسخة الاحتياطية فاسدة | **توقف — لا تنفّذ**؛ راجع القرص والمساحة ثم أعد المحاولة؛ القاعدة الأصلية لم تُمسّ |
| `platform_frozen` | تجميد إداري أثناء نقل | أكمل النقل أو ألغه |
| `no_pending_rotation` | لا تأكيد تدوير معلَّق | ربما أكّدته سابقًا |
